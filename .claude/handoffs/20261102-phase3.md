## 3A Checklists: repeating lists, sub-tasks, event prep lists
### Data
- `Checklist.repeat String @default("none")` (none | daily | weekly), `Checklist.repeat_weekday Int?` (0 Sunday to 6), `Checklist.last_reset_on DateTime? @db.Date`.
- `ChecklistItem.parent_id String?` self-relation (onDelete Cascade), index on it. One level only: a sub-task cannot have sub-tasks; headings cannot have sub-tasks.
- `Checklist.event_id String? @unique` relation to Event (onDelete SetNull).

### Behaviour
- Repeating: owner picks Never, Every day, or Every week on <weekday> in list settings. Reset happens at 00:00 Nairobi: every task's `done_at` and `done_by_id` are cleared, assignees and due dates stay. Do the reset in two places so it is right even if the cron is late: (1) a step in the daily cron that resets all due lists, (2) a lazy check when a list is opened (`last_reset_on` before the current period start means reset first, inside the same transaction with the list row locked). Log one activity row "List reset for the new day/week". A repeating list shows a small "Repeats daily" or "Repeats on Mondays" badge.
- Sub-tasks: "Add sub-task" in the task row menu. Sub-tasks render indented under their parent, tick on their own, and the parent shows "2 of 3" progress. Ticking a parent does not tick children. Deleting a parent deletes its sub-tasks (HoldToConfirm says how many). Sub-tasks appear in My tasks and the morning email like any task.
- Event prep list: on the event detail page, a "Prep list" panel. If none, "Create prep list" makes a personal checklist titled "<event title> prep" owned by the event owner with `event_id` set, seeded with 5 starter tasks (Confirm venue, Send invites, Order refreshments, Print QR codes, Assign check-in). If one exists, show its progress and an Open link. The checklist header links back to the event. Deleting the event leaves the list.

## 3B Files, form logic, auto-delete, templates
Needs from the owner before launch: a second, PRIVATE R2 bucket (name it `nikoform-uploads`, no public URL) and its name in Vercel env as `UPLOADS_BUCKET`. Same R2 keys.

### Data
- `Upload` table: id, owner_id (who uploaded, nullable for public form visitors), bucket key, file name, mime, size, created_at, plus nullable `form_response_id` and `checklist_item_id` (onDelete Cascade on both).
- `Form.auto_delete_days Int?` (null means keep forever; allowed 30, 90, 180, 365).
- Form field JSON gains optional `show_if: { field_id, equals }` (string or string[] for choice fields). No migration needed for that, it lives in `FormVersion.fields`.

### Behaviour
- Private uploads in `src/lib/uploads.ts`: presigned PUT for upload, presigned GET (5 minutes) for download, never a public URL. Limits: 10 MB per file; images (jpeg, png, webp, heic) and pdf only; checked server side from the declared type and size, and again on confirm with a HEAD request.
- Form file/photo question: new field type `file` (one file per question). Public form uploads go through a short-lived token tied to the form, so visitors cannot upload without opening the form. Responses table and CSV show the file name; owners download through the presigned GET.
- Checklist task attachments: up to 5 files per task, any member can add, owner or uploader can remove. Shown as chips under the task notes.
- Show-if logic: in the builder's question settings, "Show this question only if" picks an earlier question and a value. Hidden questions are skipped and not required. Validation runs the same rule on the server, so a hidden required question never blocks a submit.
- Auto-delete: form settings select "Keep answers: forever, 30, 90, 180, 365 days". A step in the daily cron deletes responses older than that (and their uploads, deleting the objects from R2 first). The responses page shows "Answers older than N days are deleted automatically".
- Templates: "Start from a template" on the new form page with 5 templates defined in code (`src/lib/forms/templates.ts`): Event registration, Feedback survey, Contact request, Job application (uses the file question), Volunteer sign-up. Picking one fills the builder; nothing is saved until the owner saves.

### Files

## 3C Paystack payment question
Highest risk: real money. Codex builds it; Claude audits every line of the payment path and tests with Paystack test keys on a local build before any merge.

### Data
- Field type `payment` in the form JSON: `{ amount_kes: number (100 to 1,000,000), label }`. One per form, must be the last question.
- `FormResponse.payment_id String? @unique` relation to the existing `Payment` table; `FormResponse.status String @default("complete")` (pending_payment | complete).

### Behaviour
- Submitting a form with a payment question saves the response as `pending_payment`, creates a `Payment` through the same helpers events use (`src/lib/payments.ts`, `tokea-` reference prefix unchanged), and redirects to Paystack checkout.
- Only a verified Paystack webhook (`verifyWebhookSignature`) or a server-side `verifyTransaction` on the return page marks it paid and the response `complete`. Amount and currency are checked against the stored payment, never against anything from the browser.
- Responses table, counts and CSV show only complete responses by default, with a "Show unpaid" toggle. Unpaid responses older than 24 hours are deleted by the daily cron step.
- If Paystack is not configured (`isPaystackConfigured()` false), the builder hides the payment type and explains why.

### Files
`prisma/schema.prisma`, migration `2026110512xxxx_form_payments`, `src/lib/forms/*`, `src/lib/actions/form-submit.ts`, `src/lib/payments.ts` (reuse, do not change behaviour for events), the Paystack webhook route, `src/app/f/[slug]/*`, `src/components/forms/*`, the cron route.
